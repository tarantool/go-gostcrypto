# GOST R 34.10 — Digital Signature Algorithm (RFC 5832 / RFC 7091)

This document describes the GOST R 34.10 signature algorithm implemented by
`package gost3410sign`: what it is, its specification, the notable points of
this implementation, and the test vectors that pin it. For the public API and
a usage example see the [package README](README.md).

## What it is

GOST R 34.10 is the Russian-standard elliptic-curve digital signature
algorithm. It is structurally an **EC-Schnorr/ElGamal variant** — not
ECDSA, despite the visual similarity of the equations — defined over a
prime-field short-Weierstrass curve with GOST-specific parameter sets.

Two generations exist, sharing the *same* point arithmetic and the *same*
sign/verify equations; they differ only in the companion hash and the
supported key sizes:

| Generation | Standard | RFC | Hash | Sizes |
|---|---|---|---|---|
| GOST R 34.10-2001 | GOST R 34.10-2001 | [RFC 5832](rfc/rfc5832.txt) | GOST R 34.11-94 | 256-bit only |
| GOST R 34.10-2012 | GOST R 34.10-2012 | [RFC 7091](rfc/rfc7091.txt) | Streebog-256 / Streebog-512 | 256-bit and 512-bit |

Because the sign/verify math is identical across generations, one
implementation covers both — the only generation-dependent choice is which
digest feeds in and how wide the curve is (32-byte vs 64-byte coordinates).
Curve parameters, point arithmetic, and scalar multiplication (`Curve`,
`Point`, `ScalarMult`, `ScalarMultSecret`, `Base`, `IsOnCurve`, `CurveByOID`)
are supplied by the sibling package
[`gost3410curves`](../gost3410curves/DESIGN.md); this package never touches
field or curve arithmetic directly.

### Where this module uses it

- The root `gostcrypto` facade (`exports.go`) wraps the three functions here
  as `VerifyDigestOnCurve`, `PublicKeyRawFromPrivate`, and
  `SignDigestOnCurve`. The sign wrapper is the concrete illustration of the
  "retry on `nil`" contract: it loops (bounded, currently 64 attempts),
  drawing a fresh random nonce each time via `crypto/rand`, and calls
  `SignDigest` again whenever it returns `nil`, until a valid signature comes
  back or the attempt budget is exhausted. Two convenience wrappers —
  `PublicKeyRawFromPrivate2001Test`, `R341012Sign`, `R341012Verify` — pin the
  curve to the RFC 7091 §7.1 test parameter set (via `vko.Curve2001Test()`)
  for callers that don't need to name a curve explicitly.
- **[x509gost](../x509gost/README.md) certificate-chain verification** calls
  `VerifyDigestOnCurve` to verify a GOST-signed certificate. The hash
  algorithm is chosen from the child certificate's signature OID — GOST R
  34.11-94 for 2001 certs, Streebog-256 or Streebog-512 (see
  [`../streebog/DESIGN.md`](../streebog/DESIGN.md)) for 2012 certs — and the
  curve is resolved from the parent's public-key parameter OID. Notably,
  x509gost byte-reverses the resulting hash digest before calling
  `VerifyDigestOnCurve`: GOST signing treats the hash as a *little-endian*
  integer, but `VerifyDigest` here reads its `digest` argument big-endian (see
  the digest convention below), so the natural big-endian-displayed output of
  `hash.Hash.Sum` must be reversed first. This was established empirically
  against externally-generated certificates (OpenSSL + gost-engine) and is
  pinned by x509gost's own external-fixture tests.
- **VKO key exchange** (`vko`) uses `gost3410curves` directly for its own
  `d·P` scalar multiplication; it does not call into this package. The root
  facade's `PublicKeyRawFromPrivate2001Test` pairs `PublicKeyRaw` here with
  `vko.Curve2001Test()` purely as a shared curve constant, not a dependency
  between the two packages.

This primitive is not in the per-record hot path of any mode — it fires once
per certificate during a TLS handshake, via x509gost.

## Specification

All numbered references below are to RFC 7091 (2012); the 2001 step numbering
in RFC 5832 is identical.

### Domain parameters (the curve)

A GOST R 34.10 curve in canonical short-Weierstrass form is
`y² = x³ + a·x + b (mod p)` with:

- `p` — characteristic of the prime field. 256-bit curves: `p.BitLen() <= 256`,
  coordinate size 32 bytes. 512-bit curves: `p.BitLen() > 256`, coordinate
  size 64 bytes.
- `a`, `b` — curve coefficients.
- `q` — order of the cyclic subgroup generated by the base point. Both `r`
  and `s` live mod `q`.
- `(x, y)` — base point `P`.
- cofactor — 1 for the prime-order subgroups in common use.

The full parameter sets (both the CryptoPro-2001 and TC26-2012 OID-resolvable
curves, and the RFC 7091 §7.1/§A.2 test parameter sets used below) are
tabulated in RFC 7836 §3 and implemented in
[`gost3410curves`](../gost3410curves/DESIGN.md).

### Point arithmetic

Affine short-Weierstrass over `GF(p)`: point addition/doubling via the
standard slope formula, and scalar multiplication `k·P` via a double-and-add
ladder. All of this lives in `gost3410curves` —
[`Add`/`Double`](../gost3410curves/DESIGN.md) for the group law,
`ScalarMult`/`ScalarMultSecret` for the ladder (the latter selects a
constant-time implementation for secret scalars when `Curve.ConstantTime` is
set — see [Implementation notes](#implementation-notes) below). This package
only ever calls those entry points; it has no notion of projective
coordinates or ladder internals of its own.

### Signature generation (RFC 7091 §6.1)

Input: message hash `H` (32 or 64 bytes), private key `d` (integer
`0 < d < q`), nonce `k`.

1. **§6.1 step 2** — interpret `H` as integer `alpha` and reduce:
   `e = alpha mod q`. *"If e = 0, then assign e = 1."*
2. **§6.1 step 3** — `k`, `0 < k < q` (caller-supplied here; see below).
3. **§6.1 step 4** — `C = k·P`; `r = x_C mod q`. If `r = 0`, the caller must
   retry with a new `k`.
4. **§6.1 step 5** — `s = (r·d + k·e) mod q`. If `s = 0`, retry.
5. **§6.1 step 6** — output `zeta = (R || S)`.

### Signature verification (RFC 7091 §6.2)

Input: `H`, public key point `Q`, signature `(r, s)`.

1. **§6.2 step 1** — reject unless `0 < r < q` and `0 < s < q`.
2. **§6.2 step 3** — `e = alpha mod q`; if `e = 0`, `e = 1`.
3. **§6.2 step 4** — `v = e⁻¹ mod q`.
4. **§6.2 step 5** — `z1 = s·v mod q`; `z2 = −r·v mod q` (i.e. `(q − r·v) mod q`).
5. **§6.2 step 6** — `C = z1·P + z2·Q`; `R = x_C mod q`.
6. **§6.2 step 7** — valid iff `R == r`.

### Key and signature encoding

GOST encodes integers **little-endian** on the wire for keys, the opposite of
nearly every other EC stack; the digest and the packed signature halves are
each big-endian. Mixing these two conventions up is the most common source of
interop bugs against this primitive.

**Private key** (`prv` argument): `PointSize` bytes, little-endian. Parsed by
byte-reversing the input, then reducing mod `q`; a zero key is rejected.

**Public key** (`pubRaw` / `PublicKeyRaw`'s return): `2·PointSize` bytes, the
concatenation `LE(X) || LE(Y)`:

```
256-bit pubkey (64 bytes total):  [ LE(X) : 32 ] [ LE(Y) : 32 ]
512-bit pubkey (128 bytes total): [ LE(X) : 64 ] [ LE(Y) : 64 ]
```

**Signature** (`sig` argument / return): `2·PointSize` bytes laid out
**`pad(s) || pad(r)`** — `s` FIRST, `r` SECOND (not the RFC's `R||S` writing
order) — each big-endian within its own half:

```
256-bit signature (64 bytes):  [ s : 32 BE ] [ r : 32 BE ]
512-bit signature (128 bytes): [ s : 64 BE ] [ r : 64 BE ]
```

**Digest**: read big-endian (`big.Int.SetBytes` of the bytes exactly as
handed in — RFC 7091 §5.3), never byte-reversed by this package. Callers that
feed it a hash whose "natural" integer interpretation is little-endian (as
GOST signing conventionally treats a hash) must reverse the digest bytes
themselves before calling in — see the x509gost usage note above for a
concrete example of exactly this reversal.

## Implementation notes

Points where a naive reading of the RFC is easy to get backwards; each is
exercised by a test vector below.

1. **Digest-as-integer is read big-endian, never reversed.** `SignDigest`
   and `VerifyDigest` both do `e := new(big.Int).SetBytes(digest)` directly —
   no byte-reversal step. The RFC 7091 §7 KAT digest
   `2dfbc1b3…2b043ee5`, read big-endian and reduced mod `q`, equals the
   published `e = 0x2DFBC1B3…2B043EE5` exactly; reading it little-endian
   would give a different (wrong) `e` and the §7 signature would not verify.

2. **`e = 0 → e = 1` substitution.** RFC 7091 §6.1/§6.2 mandate it in both
   sign and verify. Without it, a digest that reduces to `0` mod `q` makes
   `v = e⁻¹` undefined in `VerifyDigest`.

3. **`z2` sign handling.** The RFC states `z2 = −r·v mod q`. This package
   computes `z2 = r·v mod q` then `z2 = q − z2`, `z2 mod q` — i.e. it
   normalizes the negation to stay non-negative rather than relying on
   `math/big`'s signed-result `Mod` semantics for a negative intermediate.

4. **Signature half-ordering is `s||r`, NOT `r||s`.** Despite the RFC writing
   the signature as `R||S` (`r` first) in §6.1 step 6, the packed byte form
   both `SignDigest` and `VerifyDigest` produce/consume is `s` then `r`. Get
   this backwards and verification silently fails rather than erroring.

5. **Public-key `Raw` is `LE(X)||LE(Y)`.** `PublicKeyRaw` writes each
   coordinate little-endian independently into its own half (`putLE`); there
   is no single whole-buffer reverse trick to reproduce here, just per-half
   little-endian serialization of `X` then `Y`.

6. **Nonce `k` is reduced mod `q` on load, not validated as `< q`.**
   `SignDigest` reads `k` big-endian and reduces it mod `q`, returning `nil`
   if the reduction is zero. RFC §6.1 step 3 asks for `0 < k < q`; this
   package achieves that by reduce-then-reject-zero rather than rejection
   sampling. The root facade's `signDigestOnCurve` wrapper (see "Where this
   module uses it") performs true rejection sampling one layer up: it draws a
   full-width uniform `k` from `crypto/rand` and only serializes it (as bytes
   `SignDigest` will reduce) once it's non-zero, retrying the whole draw on a
   `nil` result from `SignDigest` — i.e. degenerate nonces are resampled by
   the caller, not silently coerced by this package.

7. **`r==0` and `s==0` are caller retry points, not internal loops.**
   RFC §6.1 steps 4/5 require regenerating `k` when either lands on zero.
   `SignDigest` has no RNG of its own — it takes `k` as an argument — so it
   cannot retry internally; it signals the retry condition by returning
   `nil`, matching the "returns `nil` on a degenerate input" contract
   documented on the function.

8. **Verify's range check is strict on both ends.** `VerifyDigest` rejects
   `r ≤ 0 || r ≥ q || s ≤ 0 || s ≥ q`. A value equal to `q` must be rejected
   outright, not reduced into range.

9. **512-bit sizing is driven entirely by `Curve.PointSize()`, never a
   hardcoded `32`.** Both functions size their input/output buffers off
   `c.PointSize()`, so the same code path handles the 256-bit CryptoPro/TC26
   curves and the 512-bit TC26 curves without a separate code path.

10. **The constant-time knob is transparent to signature bytes.**
    `Curve.ConstantTime` (in `gost3410curves`) selects between
    `ScalarMultSecret`'s constant-time and reference-timing ladders for the
    two secret-scalar multiplications this package performs (`k·P` in
    `SignDigest`, `d·P` in `PublicKeyRaw`); verification's public-scalar
    multiplications always use the reference path regardless. Toggling the
    flag must never change the produced signature or public key — this is
    pinned directly by a dedicated test (see Conformance testing below).

## Test vectors

### Primary inline KAT — RFC 7091 §7 (256-bit TestParamSet)

This is the canonical GOST R 34.10-2012 256-bit example. The **keys** are
shown **little-endian** (the form `PublicKeyRaw`/`prv` use); the **digest**
and the **signature halves** are **big-endian**. The RFC publishes the
underlying integers big-endian; both forms are given so you can cross-check.

**Curve (id-GostR3410-2001-TestParamSet)** — equal to RFC 7091 §7.1
(big-endian integers):

```

P.y = 0x08E2A8A0E65147D4BD6316030E16D19C85C97F0A9CA267122B96ABBCEA7E8FC8

```

  2dfbc1b372d89a1188c09c52e0eec61fce52032ab1022e8e67ece6672b043ee5
  (numerically e = alpha mod q from RFC §7.2: 0x2DFBC1B3…2B043EE5.

makes `VerifyDigest` return `false`.

### GOST R 34.10-2012 Appendix A.2 — 512-bit worked example

The same three properties (public-key derivation, deterministic signing with
the published nonce, verification, and tamper rejection) hold for the
standard's 512-bit example curve (`id-tc26-gost-3410-2012-512-TestParamSet`),
proving the implementation's `PointSize`-driven sizing extends correctly to
64-byte coordinates. See `gost3410sign_test.go`'s `katPrv512LE`/`katDig512BE`/
`katNonce512`/`katR512`/`katS512` constants for the full hex.

### Property coverage

The test suite additionally pins:

- **Round-trip across all twelve OID-resolvable curves** (5× CryptoPro-2001
  incl. XchA/B, 4× TC26-2012-256, 3× TC26-2012-512) with deterministic,
  curve-sized private key / digest / nonce inputs — proving the curve-generic
  path and the 32-vs-64-byte sizing switch.
- **Rejection paths**: malformed lengths (nil/short/long `sig`/`pubRaw`),
  out-of-range `r`/`s` at both ends (`0`, `q`, values above `q`), an
  off-curve public key, degenerate signing inputs (zero private key, zero
  nonce), and the `e = 0 → e = 1` substitution.
- **Bit-flip sweep** and fuzz targets (`FuzzVerifyNeverPanics`,
  `FuzzSignVerifyRoundTrip`) confirming `VerifyDigest` never panics on
  arbitrary byte input and that sign-then-verify round-trips hold under
  randomized fuzzing.
- **Constant-time transparency**: `TestConstantTime_MatchesReference` signs
  and derives a public key twice — once with `Curve.ConstantTime = false`,
  once with `true` — and asserts byte-identical output, plus that the
  constant-time-produced signature still verifies.

## Conformance testing

The in-package tests (`gost3410sign_test.go`, `rejection_test.go`,
`ct_config_test.go`) anchor all of the fixed vectors and properties above. In
addition, a differential fuzz harness compares this implementation against an
independent reference over random private keys and digests on a fixed curve:
(1) sign-then-verify round-trips for every fresh `(d, digest)`, since signing
is randomized and the signature bytes themselves cannot be pinned for a
random nonce; and (2) cross-verification — a signature produced by this
implementation must verify under the reference implementation and vice
versa, since verification *is* deterministic.

```sh
go test ./gost3410sign/
```
